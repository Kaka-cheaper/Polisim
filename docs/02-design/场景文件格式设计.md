# 场景文件格式设计

## 一、文档目标

本文件定义 `Scenario` 的第一版文件格式，用于表达一次具体仿真的实例化内容。

`Scenario` 负责回答：

1. 这次仿真里有哪些具体实体
2. 它们的初始属性是什么
3. 初始关系是什么
4. 环境初始状态是什么
5. 要跑多少轮
6. 哪些事件和断点需要预设

## 二、职责边界

`Scenario` 只定义一次仿真的实例化内容。

它负责：

1. 实体实例
2. 初始属性值
3. 初始关系
4. 环境初始值
5. 预设事件
6. 断点
7. 轮次与运行配置
8. 当前场景的观测与暂停开关

它不负责：

1. 定义新的实体类型
2. 定义新的动作类型
3. 定义新的消息类型
4. 定义通用分析算法

这些属于 `World Definition` 或分析模块。

## 三、顶层结构

```yaml
version: "0.1"
world_id: market-competition
rules_module: "rules.market_competition:MarketCompetitionRules"  # 可选（D-010）
scenario:
  id: market-demo-001
  name: 区域市场竞争推演

entities: []
relations: []
environment: {}
scheduled_events: []
breakpoints: []
config: {}
```

## 四、字段设计

### 4.0 rules_module（D-010 新增）

用于声明本次仿真使用的规则模块。

格式：``"module.path:ClassName"``，例如 ``"rules.minimal_market:MinimalMarketRules"``。

- 冒号左侧：Python 导入路径（允许多级点号分隔）
- 冒号右侧：单个类名，必须继承自 `rules.base.BaseRules`
- 字段**可选**：未声明时 Runtime 需由调用方显式传入 `BaseRules` 实例

由 `core/rules_loader.load_rules_class` 解析为类对象（不是实例——由 Runtime 根据
`RuntimeConfig` 决定构造参数，例如注入 `random_seed`）。

**为什么放在场景层而不是世界层**：同一个 world 可能搭配不同规则做对照实验
（例如 "温和监管"版 vs "严厉监管"版），rules 归属场景（一次仿真的完整描述）
而非世界（静态结构）。详见 D-010 决策与 D-009 路线 1。

### 4.1 scenario

```yaml
scenario:
  id: market-demo-001
  name: 区域市场竞争推演
  description: 首个 MVP 验证场景
```

### 4.2 entities

用于定义具体实体实例。

建议结构：

```yaml
entities:
  - id: company_a
    type: Company
    name: 企业A
    attributes:
      market_share: 25
      cash: 120
      reputation: 60
      strategy_bias: aggressive
  - id: regulator_main
    type: Regulator
    name: 主监管方
    attributes:
      strictness: 60
      credibility: 80
      pressure_level: 20
      intervention_threshold: 70
```

约束：

1. `id` 必填且唯一
2. `type` 必须能在 `World Definition` 中找到
3. 未填写的属性使用 `World Definition` 默认值
4. `entities` 数组至少包含一个元素（`minItems: 1`，空场景无法推进仿真）

### 4.3 relations

用于定义初始关系。

建议结构：

```yaml
relations:
  - type: competition
    source: company_a
    target: company_b
    value: 1.0
  - type: supply_dependency
    source: company_a
    target: supplier_main
    value: 0.8
```

约束：

1. `type` 必须能在 `World Definition` 中找到
2. `source` 和 `target` 必须引用已有实体

### 4.4 environment

用于定义初始环境变量值。

建议结构：

```yaml
environment:
  market_demand: 55
  policy_pressure: 30
  public_sentiment: 5
  resource_cost: 40
  risk_level: 20
```

未填写的环境变量使用 `World Definition` 默认值。

### 4.5 scheduled_events

用于定义在特定轮次注入的环境事件。

建议结构：

```yaml
scheduled_events:
  - tick: 5
    type: environment_event
    name: raw_material_cost_rise
    payload:
      resource_cost_delta: 15
  - tick: 10
    type: message_injection
    message:
      type: policy_signal
      delivery: broadcast
      payload:
        signal: 加强审查
        strength: 80
```

### 4.6 breakpoints

用于定义自动暂停条件。

建议结构：

```yaml
breakpoints:
  - id: high_risk
    when:
      environment:
        risk_level:
          gte: 80
  - id: company_a_low_cash
    when:
      entity:
        id: company_a
        attribute: cash
        lte: 20
```

第一版只支持简单条件断点，不支持复杂布尔表达式。

### 4.7 config

用于定义运行参数。

边界原则：

1. `Scenario.config` 只定义“这次仿真如何运行”
2. 不定义通用分析算法
3. 不定义通用规则逻辑
4. 不重复定义世界级默认值

建议结构：

```yaml
config:
  total_ticks: 30
  max_ticks: 40
  pause_mode:
    manual: true
    every_tick: false
  snapshot_mode: every_tick
  analysis:
    snapshot_fields: [entities, relations, environment, messages]
```

约束：

1. `total_ticks` 必填
2. `max_ticks` 必须大于等于 `total_ticks`

字段说明：

1. `pause_mode`
   - 当前场景的暂停策略
2. `snapshot_mode`
   - 当前场景的快照保存频率
3. `analysis.snapshot_fields`
   - 当前场景要求保留的最小分析字段集，不包含分析算法本身

第一版允许放在 `Scenario.config` 中的内容主要包括：

1. 轮次上限
2. 暂停策略
3. 快照频率
4. 需要保留的分析字段范围

第一版不应放在 `Scenario.config` 中的内容包括：

1. 动作前置条件
2. 动作效果解释逻辑
3. 冲突处理算法实现
4. 通用报告生成算法

第一版的 `analysis` 只允许表达“为了分析需要保留什么数据”，不允许表达“如何分析这些数据”。

## 五、最小完整示例

```yaml
version: "0.1"
world_id: market-competition
scenario:
  id: market-demo-001
  name: 区域市场竞争推演

entities:
  - id: company_a
    type: Company
    name: 企业A
    attributes:
      market_share: 25
      cash: 120
      reputation: 60
      strategy_bias: aggressive
  - id: company_b
    type: Company
    name: 企业B
    attributes:
      market_share: 20
      cash: 100
      reputation: 55
      strategy_bias: balanced
  - id: regulator_main
    type: Regulator
    name: 主监管方
    attributes:
      strictness: 60
      credibility: 80
      pressure_level: 20
      intervention_threshold: 70

relations:
  - type: competition
    source: company_a
    target: company_b
    value: 1.0

environment:
  market_demand: 55
  policy_pressure: 30
  public_sentiment: 5
  resource_cost: 40
  risk_level: 20

scheduled_events:
  - tick: 5
    type: environment_event
    name: raw_material_cost_rise
    payload:
      resource_cost_delta: 15

breakpoints:
  - id: high_risk
    when:
      environment:
        risk_level:
          gte: 80

config:
  total_ticks: 30
  max_ticks: 40
  pause_mode:
    manual: true
    every_tick: false
  snapshot_mode: every_tick
```

## 六、校验规则

第一版至少校验以下内容：

1. `world_id` 必须存在且与加载的世界定义一致
2. 所有实体 `id` 唯一
3. 所有实体 `type` 合法
4. `entities` 数组不得为空
5. 所有关系引用的实体必须存在
6. 所有环境变量必须在世界定义中声明
7. 所有事件 `tick` 必须大于等于 1
8. `total_ticks` 必填，`max_ticks >= total_ticks`

### 6.1 必填 vs 可选字段

第一版 schema 的 `required` 列表只包括：

1. `version`
2. `world_id`
3. `scenario`
4. `entities`
5. `config`（其中 `config.total_ticks` 必填）

以下字段为可选，未提供时视为"空"：

1. `relations` → 默认 `[]`（无初始关系）
2. `environment` → 默认 `{}`（全部使用世界定义默认值）
3. `scheduled_events` → 默认 `[]`（无预设事件）
4. `breakpoints` → 默认 `[]`（无断点）

约定：

1. JSON Schema 层不把上述字段列为 `required`
2. Pydantic 模型通过 `default_factory=list` / `default_factory=dict` 保证消费端收到的对象始终是容器，不会出现 `None`
3. Loader 不需要额外做"空填充"逻辑
4. 消费端（`Runtime` / `Rules` / 分析层）可以无条件按容器语义处理这些字段

这条约定的目的是：

**让最简场景能真正"最小"，同时保证消费端的结构稳定性与严格模式下完全一致。**

## 七、第一版不做什么

第一版不在 `Scenario` 中支持：

1. 动态 include 多文件
2. 复杂脚本条件
3. 实时外部数据接入
4. 参数搜索批量实验定义

第一版只解决一件事：

**让一次仿真可以被完整、明确、可校验地实例化。**
