# 实现映射设计

## 一、文档目标

本文件是从“系统设计”过渡到“代码实现”的桥梁。

它不新增新的设计概念，只做一件事：

**把现有文档中的分层设计映射成未来代码结构与实现顺序。**

## 二、为什么现在需要这份文档

到当前阶段，项目已经具备：

1. 总览文档
2. 需求文档
3. MVP 场景文档
4. 设计层文档

下一步如果直接开始写代码，最大的风险不是方向错，而是：

1. 工程实现把不同层重新写混
2. 代码目录结构和设计文档无法一一对应
3. 开发顺序不对，导致返工

因此需要一份实现映射文档，把设计层和代码层对齐。

### 3.1 关于 tests/

`tests/` 不是原始设计文档里的分层之一，但它是 `docs/01-requirements/验收标准.md` 的直接载体——每条"通过标准"最终都要以可运行的测试来固化。

约定：

1. 每个 `models/` 下的模块都对应一份 `tests/test_<module>.py`
2. 每个 `core/` 下的 loader / runtime / analysis 模块都对应一份 `tests/test_<module>.py`
3. 测试文件按"合法路径 + 边界拒绝 + 跨层边界固化"三类组织
4. 每条测试要么引用 `验收标准.md` 某一节，要么固化一个已决策（如 D-001 / D-003）的行为
5. 如果某个测试难以归入任一验收项，说明这次实现超出了当前阶段范围——按 `验收标准.md` 第 17.1 节处理

## 四、设计层到代码层的映射

### 4.1 World Definition

设计来源：

- `世界定义文件格式设计.md`

代码落点建议：

1. `schemas/world_definition.schema.json`
   - 定义世界配置的 JSON Schema
2. `models/world_models.py`
   - 用 Pydantic 定义内部结构化模型
3. `core/definition_loader.py`
   - 负责加载、校验、标准化

### 4.2 Scenario

设计来源：

- `场景文件格式设计.md`

代码落点建议：

1. `schemas/scenario.schema.json`
2. `models/scenario_models.py`
3. `core/scenario_loader.py`

### 4.3 Rules

设计来源：

- `规则层设计.md`

代码落点建议：

1. `rules/base.py`
   - 第一版规则接口与默认实现（`BaseRules` ABC + 3 项通用方法）
2. `rules/minimal_market.py`
   - MVP 场景下的具体规则实现（只覆写 `resolve_effects`，其他继承）
3. `core/rules_loader.py`（D-010）
   - `load_rules_class(rules_module: str) -> type[BaseRules]` 动态加载器
   - 把 `Scenario.rules_module`（形如 ``"rules.minimal_market:MinimalMarketRules"``）解析为类对象
   - 校验：格式、模块存在、类存在、是类、是 `BaseRules` 具体子类

第一版不需要单独配置化规则 DSL，因此规则先落在代码模块里，而不是 `rules.yaml` 或 `rules.schema.json`。

这意味着：

1. v1 的 `Rules` 是**独立层**，但它的表达方式是代码接口，不是文件 schema
2. `schemas/` 中不放 `rules.schema.json`
3. 场景通过 `rules_module` 字段**显式**引用对应规则模块（D-010），不直接承载规则实现
4. 未声明 `rules_module` 时，Runtime 仍可由调用方（CLI / 测试）显式传入 `BaseRules` 实例——灵活性保留

### 4.4 Runtime

设计来源：

- `运行时与事件轨迹设计.md`

代码落点建议：

1. `models/runtime_models.py`
    - WorldState、ActionProposal、EventRecord、Snapshot、**Intervention**
2. `core/runtime.py`
    - tick 主循环、消息时序、调度、动作执行框架

**D-008 约束**：`Runtime` 落成**类**而非纯函数，暴露步进式 API：

- `step() -> TickResult`——推进一个 tick，返回本 tick 产生的事件与快照
- `run_until(tick: int)`——连续推进到指定 tick
- `pause() / resume()`——暂停/恢复
- `get_state() -> WorldState`、`get_snapshot(tick: int) -> Snapshot`
- `intervene(intervention: Intervention)`——应用干预并同时写 `intervention_applied` 事件

这套接口同时满足：`需求分析.md` 8 节暂停/干预流程、`验收标准.md` 10 节交互验收、
以及未来 UI 通过 WebSocket/SSE 对接的需求（不修改内核）。

### 4.5 Event Log

设计来源：

- `运行时与事件轨迹设计.md`

代码落点建议：

1. `core/events.py`
   - 事件记录、快照记录、append-only log
2. `models/runtime_models.py`
   - EventRecord / Snapshot 数据模型

**D-006 / D-007 约束**——事件与快照必须 UI-ready 且按 run 归档：

- 所有产物落到 `{StorageConfig.runs_root}/<run_id>/`（`run_id` 默认可读格式
  `YYYYMMDD_HHMMSS_<world>_<scenario>`）
- 事件走 `events.jsonl`，一行一 `EventRecord`，流式追加；快照按 tick 切分为
  `snapshots/tick_<N>.json`
- 落盘格式严格 JSON/JSONL/MD，便于第二阶段 UI 直接消费
- `core/events.py` 的对外接口要支持**只追加**语义（不提供 update / delete），
  并提供基于 tick / kind / actor_id 的读取过滤器

### 4.6 LLM 决策协议

设计来源：

- `LLM决策协议设计.md`

代码落点建议：

1. `models/llm_models.py`
    - LLM 输入输出 schema
2. `core/llm_policy.py`
   - 负责 prompt 组织、校验、重试、降级；**只依赖 `core/providers/base.LLMProvider` ABC**
3. `core/providers/`
   - D-005: Provider 抽象层
   - `base.py` 定义 `LLMProvider` ABC（`generate(prompt, **kwargs) -> str`）
   - `mock.py`——第 2~4 步使用，返回可复现的结构化输出，无需 API key
   - `openai.py` / `anthropic.py`——第 5 步实装，分别封装真实 SDK
   - 所有实现必须与 `LLMConfig.provider: Literal["openai", "anthropic", "mock"]` 枚举一一对应
4. `core/runtime.py`
   - 在调度中调用决策器；构造函数接收 `provider: LLMProvider`，不感知具体实现

### 4.7 分析层

设计来源：

- `分析层设计.md`

代码落点建议：

1. `core/analysis.py`
   - 即时分析与最终报告共享的摘要逻辑
2. `core/events.py`
   - 提供轨迹读取接口

### 4.8 系统配置

设计来源：

- `可用性与价值评估.md`
- `LLM辅助建模方案.md`

代码落点建议：

1. `config/llm.yaml`
   - LLM provider、模型、超时等系统级配置
2. `config/runtime.yaml`
   - 运行时全局默认参数
3. `config/storage.yaml`
   - 事件轨迹、快照、持久化相关配置
4. `config/logging.yaml`
   - 日志配置

这类配置不属于 `World Definition / Scenario / Rules` 三层业务建模文件，因此应独立放在 `config/` 中。

### 4.9 为什么目录结构要这样调整

这次调整不只是为了加 `config/`，还修正了几个工程角度的问题：

1. `core/` 不再把所有职责平铺成同级文件，避免后续继续膨胀
2. `rules/` 独立出来，明确它是一个独立代码层，而不是 `core/runtime.py` 的附属物
3. `scenarios/` 比 `examples/` 更准确，因为这里放的是可运行场景包，不只是示例说明
4. `cli/` 比 `app/runner.py` 更直接，第一版本质上需要的是运行入口，不是完整应用层
5. `models/` 补上 `config_models.py`，保证系统配置也有结构化模型

### 4.10 API 服务层（v0.2，D-017）

设计来源：

- `docs/02-design/decisions/D-017-v0.2-API契约与Server架构.md`

代码落点建议：

1. **`server/api/v1/routes/`**——FastAPI 路由 handler，只做 HTTP 协议层
   - 业务逻辑**必须委托给 services/**——不直接调 `core/runtime`
2. **`server/services/`**——业务逻辑层（与 HTTP 解耦）
   - 可被 CLI / mobile / 第三方 SDK 同时复用
3. **`server/runtime_registry.py`**——多并发 Runtime 实例的内存注册表
   - 限制 `max_concurrent_runs`（v0.2 默认10）；idle GC
4. **`server/api/v1/errors.py`**——`SimEngineError` 子类→HTTP 状态码映射
   - 统一 `ErrorResponse` 格式（`{error: {code, message, issues?}}`）
5. **`server/api/v1/ws_events.py`**——WebSocket 所有事件的 typed message schema
   - `tick_advanced` / `paused` / `run_finished` / `error` / `ping` / `pong`

**数据 schema 复用纪律**：response_model 直接用 `models/*` 的 Pydantic，不新建翻译层。**v0.2 新增平台专有 schema**（CreateRunRequest / RunSummary / EventListResponse 等）落点在 `server/api/v1/`——不侵入 `models/`。

**与 v1 内核的关系**：server 层只通过 `core/runtime.Runtime` + `core/events.EventLog` + `core/analysis.analyze_run/enhance_with_llm` 公开 API 消费数据——不改 v1 内核代码。

### 4.11 前端层（v0.2，D-017）

设计来源：

- `docs/02-design/decisions/D-017-v0.2-API契约与Server架构.md`
- session 30 起草的 UI mockup 文档（位置待定）

代码落点：`web/` 独立 npm 项目（Vite + React + TS + Tailwind + shadcn/ui）。

**与 server 层的关系**：

- 前端**只通过 HTTP / WebSocket** 连接 server——零知识 `core/` / `rules/` / `models/`的 Python 代码
- TypeScript 类型从 OpenAPI doc 自动生成（`openapi-typescript`），与 Pydantic 模型同步
- 主要区块（session 30 UI mockup 文档出详细列表）：主 time line / 实体状态面板 / 关系图 / 环境变量折线 / LLM 决策实时面板 / 干预控制

**GitHub Pages 静态 demo 分叉**（v0.2 收尾）：在 `web/` 中增加 "静态模式"——读预生成的 sample runs JSON，不连 server。独立部署到 `kaka-cheaper.github.io/Polisim/` 作为项目访客入口。

## 五、第一版最小实现顺序

不要一上来全做完。

第一版建议按下面顺序实现：

### 第一步：配置校验与加载

先实现：

1. `world_definition.schema.json`
2. `scenario.schema.json`
3. `definition_loader.py`
4. `scenario_loader.py`
5. `config_models.py`

目标：

能够稳定加载 `world.yaml` 和 `scenario.yaml`，并得到内部对象。

### 第二步：运行时最小骨架

再实现：

1. `WorldState`
2. `EventRecord`
3. `Snapshot`
4. 最小 tick 主循环

目标：

先不接真实 LLM，也能推进 1~2 个 tick。

### 第三步：规则层最小骨架

实现：

1. `validate_action`
2. `resolve_effects`
3. `apply_constraints`
4. `rules/minimal_market.py`

目标：

让最小动作可以被规则化执行。

### 第四步：最小示例跑通

实现：

1. `scenarios/minimal_market/world.yaml`
2. `scenarios/minimal_market/scenario.yaml`
3. `rules/minimal_market.py`
4. `cli/run.py`

目标：

跑通 walkthrough 里的最小双实体例子。

### 第五步：接入 LLM 决策协议

实现：

1. LLM 输入上下文构造
2. 输出校验
3. 重试与降级
4. `config/llm.yaml` 对应的系统配置读取

目标：

让一个真实的 `llm` 实体参与动作选择。

### 第六步：补分析层

实现：

1. 轨迹摘要逻辑
2. 即时分析
3. 最终报告
4. LLM 增强（Phase C，可选）——`core/analysis.enhance_with_llm` 接 `LLMProvider` + `RuntimeConfig`，
   为 `AnalysisResult` 填补 `narrative_summary` / `situation_judgement` / `next_action_suggestions`
   三段叙事字段；CLI 通过 `--llm-enhance` 显式启用，失败时降级保留 Phase A 报告

目标：

让暂停分析和结束报告真正基于轨迹运行；可选地用 LLM 把结构化分析升级为面向人的叙述报告。

## 六、第一版最小可运行目标

第一版不要追求完整产品。

最小成功标准应该是：

1. 有一份合法的 `World Definition`
2. 有一份合法的 `Scenario`
3. Runtime 能跑完 3~5 个 tick
4. Event Log 和 Snapshot 能正确记录
5. 最小规则能生效
6. 一个 `llm` 实体能输出合法动作
7. 能生成一次即时分析或最终报告

## 七、第一版不该做什么

在这份实现映射里，第一版不建议同时做：

1. UI
2. 分布式运行
3. 规则 DSL
4. 复杂插件系统
5. 多场景模板库
6. 全自动建模助手

这些都会把“从设计过渡到实现”这一步拖慢。

## 八、如何使用这份文档

如果你接下来准备真正开工，推荐顺序是：

1. 先看这份文档，知道设计如何映射成代码
2. 再看 `世界定义文件格式设计.md`
3. 再看 `场景文件格式设计.md`
4. 再看 `规则层设计.md` 和 `运行时与事件轨迹设计.md`
5. 最后看 `LLM决策协议设计.md` 和 `分析层设计.md`

这样可以避免一开始就把所有层混在一起实现。

## 九、最终结论

这份文档的作用不是增加新设计，而是把你已经做好的设计变成：

**可以直接开始拆代码、建目录、写最小骨架的实现入口。**

当前第一版的最终推荐结论是：

1. `World Definition` 和 `Scenario` 走文件层 + schema 校验
2. `Rules` v1 走代码层，不走文件层
3. 系统级配置单独进入 `config/`
