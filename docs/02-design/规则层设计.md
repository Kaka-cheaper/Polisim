# 规则层设计

## 一、文档目标

本文件定义 `Rules` 层的职责与第一版表达范围。

目标：

1. 明确 `Rules` 与 `World Definition` 的边界
2. 明确哪些运行行为由规则层控制
3. 为后续实现提供一个清晰的规则归属位置

## 二、职责边界

`Rules` 不负责定义世界中有什么。

`Rules` 只负责定义：

1. 动作何时允许执行
2. 动作执行后如何产生具体状态变化
3. 冲突发生时如何处理
4. 哪些条件会触发环境变化、关系变化或状态约束

也就是说：

1. `World Definition` 定义类型、字段、允许的动作和默认策略
2. `Scenario` 定义一次具体仿真
3. `Rules` 定义“这些东西如何在运行时真正生效”

## 三、第一版规则范围

第一版规则层至少覆盖以下 4 类规则：

### 3.1 前置条件规则

决定某动作在当前状态下是否可执行。

例如：

1. `cash >= 20` 才能执行 `promote`
2. `relation exists` 才能执行某些合作类动作

### 3.2 效果映射规则

将动作参数映射为真实状态变化。

例如：

1. `promote(budget=20)` → `cash -20`、`reputation +5`
2. `seek_alliance(target)` → 发送合作消息，满足条件后建立关系

### 3.3 冲突处理规则

当两个或多个动作效果冲突时，决定最终生效方式。

例如：

1. `both`
2. `priority`
3. `random`

### 3.4 约束规则

对属性边界、关系合法性、环境变化进行约束。

例如：

1. `market_share` 不得低于 0
2. `reputation` 变化后需 clamp 到范围内

## 四、与其他层的关系

### 4.1 与 World Definition 的关系

`World Definition` 里可以存在默认规则参数，例如：

1. `defaults.conflict_resolution`
2. `defaults.fallback_action`
3. `defaults.action_effect_order`

但这不等于 `World Definition` 直接替代 `Rules`。

更准确地说：

1. `World Definition` 提供规则可用的静态定义和默认值
2. `Rules` 决定这些默认值如何被真正执行

### 4.2 与 Runtime 的关系

`Runtime` 不解释业务规则，只调用规则层。

也就是：

1. Runtime 发现某动作提议
2. Runtime 调用 Rules 做合法性检查
3. Runtime 调用 Rules 生成效果变更
4. Runtime 应用这些变更并记录事件

### 4.3 与 LLM 协议的关系

LLM 只选择动作，不解释规则。

例如：

1. LLM 可以提议 `promote`
2. 但是否允许、代价是多少、结果怎么变，都由 Rules 决定

## 五、第一版实现建议

第一版不单独设计复杂规则 DSL。

建议实现方式：

1. `World Definition` 提供静态 schema 与默认参数
2. `Rules` 在代码层以明确模块/函数存在
3. 文档层先把规则类别和归属定义清楚

第一版建议最小代码接口形态如下：

1. `validate_action(world_state, action_proposal) -> ValidationResult`
2. `resolve_effects(world_state, action_proposal) -> EffectSet`
3. `resolve_conflicts(effect_sets) -> ResolvedEffectSet`
4. `apply_constraints(world_state, resolved_effects) -> ConstrainedEffectSet`

这几个接口是代码层约定，不要求在第一版文档中进一步配置化。

也就是说，第一版先明确：

**Rules 是独立层，但规则表达本身暂时不要求配置化到 DSL。**

## 六、第一版不做什么

第一版不在规则层中支持：

1. 通用规则 DSL
2. 脚本热加载
3. 跨文件规则继承
4. 高级布尔组合表达式系统

第一版只解决一件事：

**把“规则属于哪一层”这件事彻底定死，避免后续继续把规则写回 Runtime。**
