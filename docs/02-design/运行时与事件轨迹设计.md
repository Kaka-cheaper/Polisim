# 运行时与事件轨迹设计

## 一、文档目标

本文件定义第一版 `Runtime` 与 `Event Log` 的核心设计。

目标：

1. 明确 tick 推进流程
2. 明确消息何时可见
3. 明确动作如何落地为状态更新
4. 明确事件轨迹如何记录

## 二、核心原则

### 2.1 Tick-based 主循环

第一版采用 `tick-based` 主循环。

每个 tick 代表一个决策轮次。

### 2.2 同时决策、延迟可见

同一 tick 内：

1. 所有实体基于同一快照做决策
2. 当前 tick 产生的消息在下一 tick 开始时才可见

### 2.3 状态由 Runtime 更新

LLM 不直接修改状态。

LLM 只输出“建议执行的动作”，真正的状态变化由 `Runtime + Rules` 完成。

### 2.4 仿真时间与计算时间分离

第一版必须明确区分两种时间：

1. **仿真时间**
   - 由 `tick` 推进
   - 只有当当前 tick 完整结束后，才进入下一个 tick
2. **计算时间**
   - 指 LLM 调用、校验、重试、规则计算的真实耗时
   - 不直接映射为仿真时间

这意味着：

1. LLM 在当前 tick 内重试，不会把仿真自动推进到下一 tick
2. 如果某实体在当前 tick 内重试失败或超时，处理结果仍然属于当前 tick
3. 超时后的处理方式由 `World Definition.defaults.fallback_action` 决定；若未定义，则执行 `do_nothing`，而不是把该实体顺延到下一 tick 再重试

### 2.5 实体激活调度

第一版不要求每个 tick 所有实体都参与决策。

运行时应先经过一层 `activation / scheduler`，决定“本 tick 哪些实体被激活”。

运行时的职责是**执行通用激活框架**，而不是硬编码某个场景的激活规则。

也就是说：

1. Runtime 负责读取实体类型中的 `activation policy`
2. Runtime 负责根据该策略计算当前 tick 的激活集合
3. 具体激活条件来自 `World Definition` / `Rules`
4. 换场景时应主要修改配置，而不是重写 Runtime

第一版建议支持的激活条件类型：

1. 收到新消息
2. 命中环境事件
3. 自身状态发生关键变化
4. 当前动作结束，需要下一步选择
5. 到达该实体的决策周期

未被激活的实体在当前 tick 不进行 LLM 决策，也不生成新的动作提议。

## 三、单 Tick 流程

第一版单 tick 流程如下：

1. 读取上一 tick 留下的待投递消息
2. 将这些消息投递到目标实体的收件箱
3. 处理当前 tick 应触发的 `scheduled_events`
4. 计算本 tick 被激活的实体集合
5. 基于当前世界快照并行收集被激活实体的决策
6. 对每个决策进行合法性校验与必要重试
7. 对超时或校验失败的决策执行降级
8. 统一执行合法动作
9. 生成本 tick 的事件记录与状态快照
10. 检查终止条件和断点

## 四、运行时核心对象

第一版运行时建议维护以下核心对象：

### 4.1 WorldState

保存当前世界状态：

1. `tick`
2. `entities`
3. `relations`
4. `environment`
5. `mailboxes`

### 4.2 ActionProposal

表示实体在当前 tick 的动作提议：

1. `tick`
2. `actor_id`
3. `action_type`
4. `params`
5. `decision_mode`
6. `raw_reasoning_summary`
7. `status`

### 4.3 EventRecord

表示运行时记录的事实事件：

1. `event_id`
2. `tick`
3. `kind`
4. `actor_id`
5. `payload`

### 4.4 Snapshot

表示当前 tick 结束后的全局快照：

1. `tick`
2. `entity_state_summary`
3. `relation_state_summary`
4. `environment_state`
5. `message_summary`

## 五、消息时序设计

第一版消息生命周期：

1. 某动作执行后生成消息
2. 消息进入 `outbox`
3. 当前 tick 不再被其他实体读取
4. 下一 tick 开始时由 `Runtime` 投递到目标实体 `mailbox`

注意：

1. `message_types.delivery` 只决定消息路由目标
2. Runtime 的消息时序在第一版中是统一的，不因具体消息类型而改变

这样可以保证：

1. 每个 tick 的决策基于一致快照
2. 不产生当前轮即时互相影响的因果混乱

## 六、动作执行设计

第一版动作执行统一分 4 类效果：

1. 修改自身属性
2. 修改关系
3. 发送消息
4. 修改环境变量

Runtime 只负责按照配置好的效果顺序执行动作，不在代码中写死业务顺序。

默认顺序来自 `World Definition.defaults.action_effect_order`。

第一版默认顺序为：

1. 属性变化
2. 关系变化
3. 环境变化
4. 生成消息

如果发生冲突，则交给 `Rules` 或 `World Definition.defaults.conflict_resolution` 处理。

## 七、冲突解决设计

Runtime 不负责定义冲突策略本身，只负责调用已配置的冲突策略。

第一版支持以下策略类型：

1. `both`
   - 两个效果都执行
2. `priority`
   - 按实体或动作优先级决定
3. `random`
   - 随机决定

默认值来自 `World Definition.defaults.conflict_resolution`。

## 八、暂停与断点

Runtime 只提供暂停点和断点检测机制，不定义具体场景的暂停策略。

第一版暂停触发方式来自 `Scenario.config.pause_mode` 与 `Scenario.breakpoints`：

1. 用户手动暂停
2. 每 tick 自动暂停
3. 命中 `breakpoint`

暂停发生在 **tick 完成后**，不会打断 tick 内部执行。

## 九、事件轨迹设计

第一版 `Event Log` 建议采用 append-only 结构。

快照保存频率与分析字段范围不由 Runtime 写死，主要来自 `Scenario.config.snapshot_mode` 与分析配置。

每个 tick 至少记录以下事件类型：

1. `decision_proposed`
2. `decision_rejected`
3. `decision_retried`
4. `fallback_used`
5. `action_executed`
6. `message_emitted`
7. `relation_changed`
8. `environment_changed`
9. `scheduled_event_triggered`
10. `intervention_applied`
11. `snapshot_saved`

## 十、建议的事件记录结构

```yaml
- event_id: evt_0001
  tick: 5
  kind: action_executed
  actor_id: company_a
  payload:
    action_type: promote
    params:
      budget: 20
    effects:
      reputation_delta: 5
      public_sentiment_delta: 3
```

## 十一、建议的快照结构

```yaml
tick: 5
entities:
  company_a:
    market_share: 27
    cash: 100
    reputation: 65
relations:
  - type: competition
    source: company_a
    target: company_b
    value: 1.0
environment:
  market_demand: 55
  public_sentiment: 8
messages:
  emitted: 3
  delivered_next_tick: 3
```

## 十二、分析读取原则

中期分析和最终报告都不直接读取“当前状态对象”，而是优先读取：

1. 事件轨迹
2. tick 快照
3. 关键变化摘要

这样可以保证分析基于全过程，而不是基于终态猜测。

## 十三、Runtime 对外接口（D-008）

第一版 `Runtime` 落成**类**（而非纯函数），以便同时支持 CLI、测试、未来 UI 三种使用方式，
而无需修改内核。这一决定来自 D-008。

### 13.1 设计动因

纯函数 `run(world, scenario, n_ticks) -> EventLog` 写起来简单，但：

1. 无法自然表达"暂停—分析—干预—继续"流程（`需求分析.md` 8 节）
2. 未来 UI 通过 WebSocket/SSE 对接时，需要读取"当前 tick 状态"这种查询接口
3. 测试中想验证"第 3 tick 暂停后注入干预再继续"也没有自然的切入点

因此第一版的 `Runtime` 必须是一个有状态对象。

### 13.2 类签名（代码层约定）

```python
class Runtime:
    def __init__(
        self,
        world: WorldDefinition,
        scenario: Scenario,
        rules: RulesModule,
        provider: LLMProvider,
        system_config: SystemConfig,
        run_id: str | None = None,  # 为 None 时自动生成
    ) -> None: ...

    # 推进控制
    def step(self) -> TickResult: ...
    def run_until(self, tick: int) -> list[TickResult]: ...
    def pause(self) -> None: ...
    def resume(self) -> None: ...

    # 状态查询（UI-ready）
    def get_state(self) -> WorldState: ...
    def get_snapshot(self, tick: int) -> Snapshot: ...
    def is_paused(self) -> bool: ...
    def current_tick(self) -> int: ...

    # 干预（对齐需求分析 8.3 三级）
    def intervene(self, intervention: Intervention) -> EventRecord: ...
```

`TickResult` 建议包含：本 tick 产生的 `EventRecord` 列表、该 tick 结束后的 `Snapshot`、
以及是否因断点/每轮暂停而触发暂停的标志。

### 13.3 与暂停/断点的配合

- 用户 `pause()` 调用 → 当前 `step()` 完成后不再启动下一 tick
- `Scenario.config.pause_mode.every_tick=True` → 每次 `step()` 返回后自动进入 paused 状态
- 命中 `Scenario.breakpoints` → 同上
- `resume()` 仅改变内部标志，不立即推进，下一次调用 `step()` 或 `run_until()` 才真正继续

### 13.4 与事件轨迹的配合

- 每次 `step()` 内部写入若干 `EventRecord` 到 `events.jsonl`（append-only）
- 每次 `step()` 结束后按 `Scenario.config.snapshot_mode` 决定是否写 `snapshots/tick_<N>.json`
- `intervene()` 直接追加 `EventRecord(kind='intervention_applied')`，确保可追溯

### 13.5 Intervention 三级（对应 `需求分析.md` 8.3）

| kind | 语义 | 必需字段 |
|---|---|---|
| `inject_message` | 注入一条消息到某实体或广播 | `message`（`target_actor=None` 表广播） |
| `force_action` | 强制某实体在指定 tick 执行某动作 | `target_actor` + `action` |
| `override_attribute` | 直接修改某实体属性，绕过规则 | `target_actor` + `attribute_changes` |

结构见 `models/runtime_models.Intervention`。

## 十四、第一版不做什么

第一版不在运行时中支持：

1. 分布式运行
2. 跨进程消息总线
3. 回滚型事件溯源
4. 复杂事件订阅系统

第一版只解决一件事：

**让仿真可以稳定按 tick 推进，并留下完整、可分析、可回放的轨迹。**
