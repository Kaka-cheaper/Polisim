# 分析层设计

## 一、文档目标

本文件定义第一版分析层设计。

目标：

1. 明确即时分析与最终报告的职责
2. 明确它们共享哪些输入摘要逻辑
3. 明确分析层与 `Scenario.config.analysis` 的边界

## 二、职责边界

分析层负责：

1. 读取事件轨迹与快照
2. 生成中期局势分析
3. 生成最终总结报告
4. 提取关键变化与转折点

分析层不负责：

1. 推进仿真
2. 修改世界状态
3. 定义快照保存频率
4. 定义消息路由或动作规则

## 三、输入来源

分析层统一基于以下输入：

1. `Event Log`
2. `tick snapshots`
3. 必要的关键变化摘要

即时分析与最终报告都不直接依赖“当前内存对象”，而依赖轨迹数据。

## 四、即时分析

即时分析发生在仿真暂停后。

输入范围：

1. 从 `tick 0` 到当前 tick 的事件轨迹
2. 当前 tick 快照
3. 最近几轮关键变化摘要

输出目标：

1. 当前优势方
2. 当前脆弱方
3. 最近几轮关键变化
4. 当前最大风险点
5. 当前建议

## 五、最终报告

最终报告发生在仿真结束后。

输入范围：

1. 全量事件轨迹
2. 全量 tick 快照
3. 全局关键变化摘要

输出目标：

1. 全轨迹总结
2. 关键转折点
3. 各实体最终状态比较
4. 趋势判断
5. 面向用户的建议

## 六、共享摘要逻辑

即时分析和最终报告共享同一套基础摘要逻辑：

1. 关键事件提取
2. 关键状态变化提取
3. 关系变化提取
4. 风险上升/下降信号提取

区别只在于：

1. 即时分析使用局部时间窗口
2. 最终报告使用全量轨迹

## 七、与 Scenario.config.analysis 的边界

`Scenario.config.analysis` 只负责定义：

1. 需要保留哪些分析字段

它不负责定义：

1. 如何提取关键事件
2. 如何判断转折点
3. 如何生成最终报告

这些属于分析层本身。

## 八、第一版实现建议

第一版建议采用：

1. 结构化摘要生成
2. 再交给 LLM 生成自然语言结论

也就是说：

1. 先做 deterministic 的轨迹摘要
2. 再做 LLM 的分析与表达

## 九、Phase C LLM 增强落地（session 20 实装）

本节记录第八节"LLM 生成自然语言结论"阶段的具体实现约定。

### 9.1 分层与入口

- **Phase A**（纯规则）：`core/analysis.analyze_run` → 返回 `AnalysisResult`，前 5 个字段填满，后 3 个字段（`narrative_summary` / `situation_judgement` / `next_action_suggestions`）为 None
- **Phase C**（LLM 增强）：`core/analysis.enhance_with_llm(result, provider, config) -> AnalysisResult` → 返回新对象，后 3 字段被填
- **落点统一**：Phase A/C 都在 `core/analysis.py`——不新建 `core/analysis_llm.py`（遵守 `实现映射设计.md` 第四节的单模块约定）
- **一次性 end-of-run 增强**：v1 只做"最终报告"阶段的增强；"即时分析"（tick-level）留给未来

### 9.2 Prompt 构造

- Prompt 以 Phase A 产物的 JSON dump 为核心 payload
- **剔除**已填的 3 个增强字段——避免"让 LLM 看自己的旧答案"
- 附加输出契约段——要求返回包含恰好 3 个键的 JSON
- 尾部注入语言指令（与决策层 `llm_policy.build_prompt` 一致的机制）—— `config.output_language`（默认 `"zh-CN"`）

### 9.3 响应解析

`_parse_analysis_response` 严格校验：

- 顶层必须是 JSON object
- `narrative_summary` / `situation_judgement` 必填非空字符串
- `next_action_suggestions` 必填非空 list[str]，每项非空
- 额外未知 key **容忍**（LLM 偶尔加解释性字段）
- 任何违反都抛 `LLMProtocolError`

### 9.4 错误处理

- **传输层错**（`ProviderError`）：原样上抛
- **协议层错**（`LLMProtocolError`）：原样上抛
- 本函数**不**做重试——与 `llm_policy.decide` 一致，留给 Phase B.3 统一引入

### 9.5 CLI 集成

- `run` 子命令加 `--llm-enhance` flag（默认关闭——LLM 调用要钱/要网）
- 调用链路：仿真跑完 → Phase A `analyze_run` + `write_analysis` → 若 `--llm-enhance` → `enhance_with_llm` → 用新 result **覆盖写** final.md/json
- **降级策略**：Phase C 失败 → stderr 打 warning，保留 Phase A 已落盘版本，**exit code 保持 0**（仿真本身没失败）
- **与 `--no-analysis` 互动**：`--no-analysis` 优先——整个分析段跳过，不会走到 Phase C

### 9.6 未来升级点

- 即时分析（tick-level）——目前只做 end-of-run；需要时扩展 `enhance_with_llm(..., *, window=(start_tick, end_tick))`
- Prompt 中加入 scenario 描述——当前只给 `AnalysisResult` JSON；若 LLM 表现不佳再补上下文
- 结构化输出（Pydantic + OpenAI `response_format`）——等 `LLMProvider` ABC 升级后统一上

## 十、第一版不做什么

第一版不支持：

1. 多套分析算法切换
2. 可视化分析 DSL
3. 自动指标学习
4. 图谱推理型分析
5. 即时分析 LLM 增强（Phase C 只实装 end-of-run 一次性增强；tick-level 留给未来）

第一版只解决一件事：

**让即时分析和最终报告都基于统一的轨迹摘要逻辑，而不是各自为政。**
