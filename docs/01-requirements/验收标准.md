# 验收标准

## 一、文档目的

本文件用于定义 `Polisim` 当前阶段的**验收标准**。

它的作用不是解释系统怎么设计，也不是解释代码怎么实现，而是回答：

**什么结果出现后，才算真正做成。**

今后每完成一次实现，都应优先用本文件验收，而不是先靠人工大段阅读代码判断是否完成。

## 二、适用范围

本文件适用于当前第一阶段目标：

1. 跑通分层闭环
2. 跑通最小场景
3. 证明 `World Definition + Scenario + Rules + Runtime + Event Log + Analysis` 这一结构可工作

本文件当前不用于约束：

1. 第二阶段扩展能力
2. 第三阶段语义增强层
3. UI 产品化体验

## 三、来源依据

本文件当前主要基于以下文档整理：

1. `需求分析.md`
2. `MVP场景定义.md`
3. `实现映射设计.md`
4. `运行时与事件轨迹设计.md`
5. `分析层设计.md`

如果后续这些文档发生变化，应同步检查本文件是否需要更新。

## 四、验收原则

### 4.1 以结果为准

是否通过验收，优先看：

1. 输入是否能被正确处理
2. 输出是否达到预期结果
3. 行为是否符合文档要求

而不是优先看：

1. 代码写法是否“看起来像对的”
2. 结构是否“似乎合理”

### 4.2 以可验证结果为准

每条验收标准都应该能回答：

1. 怎么验证
2. 看到什么结果算通过
3. 看到什么结果算不通过

### 4.3 以用户效果为准

如果一个功能从代码上已经实现，但用户无法感知到预期效果，则不算通过。

## 五、文档优先级

如果不同文档之间出现约束冲突，优先级如下：

1. **验收标准.md**
2. `需求分析.md`
3. `MVP场景定义.md`
4. `02-design/` 下各设计文档
5. 具体实现代码

也就是说：

**实现代码不是验收依据，验收标准才是。**

## 六、验收证据要求

每次验收至少要给出下面三类证据中的一种或多种：

1. 实际运行输出
2. 结构化日志 / 快照 / 事件轨迹
3. 明确的失败信息或通过信息

不能接受的证据包括：

1. 仅说“代码已经写了”
2. 仅说“理论上应该可以”
3. 仅说“结构看起来没问题”

### 6.1 推荐的验收记录模板

今后每次实现完成后，建议至少按下面格式记录一次：

```text
验收对象：
对应验收项：
输入：
执行方式：
实际输出：
是否通过：
备注：
```

这样做的目标是：

1. 让每次实现都能回到本文件中的具体验收项
2. 让“通过/不通过”有固定记录格式
3. 减少靠人工读代码来判断完成度

## 七、当前阶段总体验收目标

当前第一阶段只有一个总目标：

**最小场景能够在不依赖人工阅读大量代码的前提下，被验证为可正确运行。**

这个总目标拆成 6 类验收：

1. 配置层验收
2. 规则层验收
3. 运行时验收
4. 轨迹与输出验收
5. 交互验收
6. 最小闭环验收

## 八、配置层验收

### 6.1 World Definition 验收

通过标准：

1. 合法的世界定义文件可以通过 schema 校验
2. 非法字段、错误枚举值、缺失必填字段会被拒绝
3. 世界定义能被加载成结构化内部对象

验证方式：

1. 提供一份合法 `world.yaml`
2. 提供一份缺字段或字段类型错误的 `world.yaml`
3. 运行 schema 校验 + loader

通过结果：

1. 合法文件通过
2. 非法文件失败，并给出明确错误信息

### 6.2 Scenario 验收

通过标准：

1. 合法的场景文件可以通过 schema 校验
2. 非法的场景文件会被拒绝
3. `Scenario` 能被加载成结构化内部对象
4. `max_ticks >= total_ticks` 等跨字段约束会被 loader 正确检查

验证方式：

1. 提供一份合法 `scenario.yaml`
2. 提供一份非法 `scenario.yaml`
3. 运行 schema 校验 + loader

通过结果：

1. 合法文件通过
2. 非法文件失败，并明确指出错误原因

## 九、规则层验收

### 7.1 动作合法性验收

通过标准：

1. 合法动作会被接受
2. 非法动作会被拒绝
3. 非法动作不会直接污染世界状态

验证方式：

1. 构造一个满足前置条件的动作提议
2. 构造一个不满足前置条件的动作提议
3. 运行 `Rules` 校验

通过结果：

1. 合法动作进入执行阶段
2. 非法动作进入拒绝或降级路径

### 7.2 效果映射验收

通过标准：

1. 动作参数能够被正确映射成状态变化
2. 关系变化和环境变化按规则生效
3. 约束规则会在必要时修正或拒绝非法效果

验证方式：

1. 执行一个已知动作
2. 检查 effect 输出和最终状态变化

通过结果：

1. 变化符合规则预期
2. 不出现越界状态或未定义状态

## 十、运行时验收

### 8.1 Tick 推进验收

通过标准：

1. Runtime 能按 tick 正常推进
2. 消息遵守“延迟可见”规则
3. 未激活实体不会无故进入决策

验证方式：

1. 运行最小场景 3~5 个 tick
2. 观察每轮状态和消息变化

通过结果：

1. tick 正常递增
2. 当前轮发出的消息不会在当前轮被再次读取
3. 调度逻辑符合 activation 配置

### 8.2 降级与容错验收

通过标准：

1. 非法决策不会使 Runtime 崩溃
2. 超时或校验失败会走 `fallback_action`
3. 若未定义 `fallback_action`，则执行 `do_nothing`

验证方式：

1. 构造非法动作提议
2. 构造模拟超时场景

通过结果：

1. 系统继续运行
2. 事件轨迹中可看到拒绝或 fallback 记录

## 十一、轨迹与输出验收

### 9.1 Event Log 验收

通过标准：

1. 每个 tick 都能留下事件记录
2. 事件记录至少覆盖动作、消息、状态变化、快照保存
3. 事件记录可供后续分析读取

验证方式：

1. 跑一次最小场景
2. 检查事件记录输出

通过结果：

1. 事件完整存在
2. 字段可读、可追溯

### 9.2 Snapshot 验收

通过标准：

1. 每个快照能反映当前 tick 结束后的世界状态
2. 快照字段与场景配置中要求的字段范围一致

验证方式：

1. 检查 tick 结束后的快照内容

通过结果：

1. 实体、关系、环境、消息摘要与实际运行一致

## 十二、交互验收

### 10.1 暂停验收

通过标准：

1. 支持手动暂停
2. 支持每轮暂停
3. 支持条件断点暂停

验证方式：

1. 人工暂停一次
2. 开启 every_tick 模式运行一次
3. 命中 breakpoint 运行一次

通过结果：

1. 系统在 tick 结束后暂停
2. 不破坏当前状态

### 10.2 暂停后操作验收

通过标准：

1. 暂停后可以继续仿真
2. 暂停后可以请求即时分析
3. 暂停后可以进行人工干预

通过结果：

1. 三种操作均能执行
2. 操作后系统状态符合预期

## 十三、分析层验收

### 11.1 即时分析验收

通过标准：

1. 暂停后可生成中期局势分析
2. 输出至少包含：优势方、脆弱方、关键变化、当前风险点、当前建议

### 11.2 最终报告验收

通过标准：

1. 仿真结束后可生成最终报告
2. 输出至少包含：全轨迹总结、关键转折点、各实体最终状态比较、趋势判断、建议

### 11.3 分析依据验收

通过标准：

1. 分析基于事件轨迹和快照
2. 不是只看最终状态做静态总结

## 十四、最小闭环验收

这是当前阶段最关键的验收项。

通过标准：

1. 有一份合法 `World Definition`
2. 有一份合法 `Scenario`
3. 规则层可处理最小动作
4. Runtime 能推进至少 3~5 个 tick
5. Event Log 与 Snapshot 正常生成
6. 至少一个 `llm` 或 `rule` 实体能完成动作选择
7. 可在暂停后拿到即时分析，或在结束后拿到最终报告

只有以上 7 项全部成立，才算“第一阶段最小闭环通过”。

## 十五、不通过的典型情况

以下任一情况出现，都应判定为不通过：

1. schema 能过，但 loader 无法加载
2. Runtime 能跑，但轨迹记录不完整
3. 分析输出存在，但只基于终态，不基于全过程
4. 暂停存在，但暂停后无法继续、分析或干预
5. 规则存在，但非法动作会直接污染状态
6. 系统只能靠读代码才能判断有没有做成

## 十六、当前阶段不纳入验收的内容

当前第一阶段不纳入强制验收：

1. 多场景模板库
2. 复杂 UI
3. 分布式执行
4. 规则 DSL
5. 全自动建模助手
6. 第二场景复用验证
7. 语义增强层

## 十七、如何使用这份文档

今后每次做实现，都建议按下面流程：

1. 先明确这次实现对应本文件中的哪一部分验收项
2. 实现后直接用对应验收项验证
3. 验证通过后才算完成
4. 如果实现结果与本文件冲突，以本文件为准回头修正实现

### 17.1 如果你是第一次使用这份文档

最简单的使用方式是：

1. 先找到这次工作属于哪一类：配置层、规则层、运行时、轨迹、交互、分析层
2. 再找到对应章节中的“通过标准”和“验证方式”
3. 实现完成后，不先读大量代码，而是先按“验证方式”跑一次
4. 只有跑出来的结果符合“通过标准”，才算完成

如果你发现一个实现很难归到本文件中的任何验收项，那通常说明：

1. 这次实现超出了当前阶段范围
2. 或者这次实现对应的验收项还没有被定义，需要先补验收再继续开发

## 十八、当前阶段的最终通过条件

当前阶段只有一个最终问题：

**最小场景能不能在不靠人工阅读大量代码的前提下，被验证为正确运行。**

如果答案是“能”，则当前阶段通过；否则不通过。
