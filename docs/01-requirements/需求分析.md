# 需求分析

## 一、项目定位

本项目是一个**分层驱动的通用多实体仿真引擎**。

它通过世界定义文件定义世界中的实体、属性、关系、动作和规则，通过场景文件实例化具体对象和初始状态，并由运行内核推动实体交互、状态演化和消息传递，最终基于完整推演轨迹输出局势分析与建议。

## 二、要解决的问题

本项目想解决的问题是：

1. 如何让用户快速定义一个可推演的复杂世界
2. 如何让多个不同类型的实体在规则约束下持续互动
3. 如何在推演过程中暂停、观察、干预并继续运行
4. 如何在推演结束后，基于完整过程而不是单一终态输出判断和建议

## 三、核心目标

引擎第一阶段必须具备以下能力：

1. **配置化定义世界**
   - 支持通过文件定义实体类型、属性、关系、动作、消息和环境规则

2. **配置化实例化场景**
   - 支持通过文件定义具体实体、初始关系、环境变量、轮次和事件

3. **多实体持续推演**
   - 支持多个实体在多轮中基于状态和消息做决策

4. **混合决策模式**
   - 支持 `llm`、`rule`、`random` 三种决策方式

5. **消息驱动交互**
   - 实体之间不直接修改彼此属性，而是通过消息和规则影响彼此

6. **全轨迹记录**
   - 记录每一轮的状态、动作、消息和关系变化

7. **暂停与干预**
   - 用户可以中途暂停、请求即时分析、注入干预后继续仿真

8. **最终分析输出**
   - 基于全轮次轨迹输出趋势、拐点、风险和建议

## 四、核心设计原则

### 4.1 世界是数据，不是代码

领域差异主要通过世界定义文件和场景文件表达，而不是把具体场景硬编码到引擎内部。

### 4.2 引擎负责运行，不负责预设行业逻辑

引擎只负责：

1. 调度轮次
2. 管理消息
3. 调用决策器
4. 执行动作效果
5. 保存轨迹
6. 暂停、恢复、干预和分析

### 4.3 世界定义负责约束，LLM 负责选择

世界定义约束的是：

1. 实体能做什么
2. 属性如何变化
3. 关系如何变化
4. 哪些消息可以发送

LLM 决定的是：

1. 在合法动作中选哪个动作
2. 动作参数如何取值

### 4.4 预测基于轨迹，而不是基于终态

最终报告和中期分析都必须基于多轮轨迹，而不是仅根据最后一轮快照下结论。

## 五、引擎结构

### 5.1 世界定义层（World Definition）

负责定义：

1. 实体类型
2. 属性模板
3. 关系类型
4. 动作定义
5. 消息类型
6. 环境规则

### 5.2 场景实例层（Scenario）

负责定义：

1. 实体实例
2. 初始关系
3. 环境初始状态
4. 预设事件
5. 断点规则
6. 仿真配置

### 5.3 规则层（Rules）

负责定义和执行：

1. 动作前置条件
2. 动作效果
3. 冲突解决策略
4. 属性边界与合法性约束
5. 环境触发规则

### 5.4 运行层（Simulation Runtime）

负责：

1. 按轮次推进仿真
2. 管理消息投递
3. 并行收集实体决策
4. 执行动作效果
5. 保存轨迹
6. 检查终止条件
7. 响应暂停和干预

## 六、仿真模型

### 6.1 时间模型

采用：**Tick-based 主循环 + tick 内事件处理**。

每个 tick 表示一个决策轮次。

### 6.2 并行语义

采用：**同时决策、延迟可见**。

即：

1. 同一轮内所有实体基于同一快照做决策
2. 当前轮产生的消息在下一轮开始时可见

### 6.3 冲突解决

支持以下策略：

1. `both`
2. `priority`
3. `random`
4. 自定义规则

### 6.4 轮次要求

场景文件中：

1. `total_ticks` 必填
2. `max_ticks` 作为安全上限

## 七、LLM 相关要求

### 7.1 决策模式

支持：

1. `llm`
2. `rule`
3. `random`

### 7.2 LLM 输出处理

采用：**校验 -> 重试 -> 降级**。

即：

1. 结构化校验输出
2. 校验失败时重试
3. 多次失败时执行 `fallback_action`，若未定义则执行 `do_nothing`

### 7.3 感知范围

实体读取上下文时应受感知范围限制，避免上下文无限膨胀。

## 八、用户交互要求

### 8.1 暂停

必须支持：

1. 手动暂停
2. 每轮暂停
3. 条件暂停

### 8.2 暂停后操作

用户暂停后可选择：

1. 继续仿真
2. 请求即时分析
3. 进行人工干预

### 8.3 人工干预

至少支持三级：

1. 注入消息
2. 强制动作
3. 直接修改属性

所有干预必须可追溯。

## 九、输出要求

### 9.1 结构化输出

至少包括：

1. 每轮状态快照
2. 消息日志
3. 动作日志
4. 关系变化

### 9.2 分析输出

至少包括：

1. 中期局势分析
2. 最终趋势总结
3. 关键转折点
4. 风险判断
5. 建议

## 十、未来演化目标

当前推荐方案不是“纯语义定义驱动”，而是“分层混合方案”：

1. `World Definition`
2. `Scenario`
3. `Rules`
4. `Runtime`
5. `Event Log`

未来演化方向如下：

1. **第一阶段**
   - 用强类型 YAML/JSON Schema 定义世界和场景
   - 用代码实现运行内核
   - 用事件日志记录完整轨迹

2. **第二阶段**
   - 组件化运行时，提升复用性和扩展性
   - 分析模块可插拔
   - 支持第二个场景验证架构通用性

3. **第三阶段**
   - 引入可选语义增强层
   - 将世界定义与知识图谱能力对齐
   - 用于语义校验、图谱分析和外部互操作

也就是说，本项目长期目标不是让语义定义主导运行内核，而是：

**让世界定义在未来可接入语义增强层，而不是让语义增强层成为当前运行内核的唯一核心。**

## 十一、非功能要求

### 11.1 v0.1（已完成）重点关注

1. 小规模可运行
2. 结构清晰
3. 可追溯
4. 可暂停
5. 可干预
6. 可复用到第二个场景

### 11.2 v0.1 不追求

1. 大规模分布式
2. 高精度预测
3. ~~复杂 UI~~——v0.1 不做 UI 但所有输出强制 UI-ready（D-006）

### 11.3 v0.2（D-017，session 30+ 实施）

v0.2 在 v0.1 内核之上加入两层：

1. **API 服务层**（`server/`）——FastAPI WebSocket 后端，把 v1 内核暴露为 HTTP / WebSocket API
2. **前端层**（`web/`）——React 实时态势面板，消费 server API 实现：
   - 实时 tick 推进可视化（订阅 WebSocket `tick_advanced` 事件）
   - 实体属性折线 / 关系图边动态 / 环境变量曲线
   - LLM 决策实时面板（拆段渲染 D-016 的 PromptContext）
   - 暂停 / 单步 / 干预的交互控制

**v0.2 关键设计纪律**（详见 `docs/02-design/decisions/D-017-v0.2-API契约与Server架构.md`）：

- **不侵入 v1 内核**——server 通过 `core/runtime.Runtime` + `core/events.EventLog` 公开 API 消费数据，v1 代码不动
- **数据 schema 复用**——response_model 直接用 `models/*` 的 Pydantic（EventRecord / Snapshot / TickResult / PromptContext / Intervention / AnalysisResult），不新建翻译层
- **三层抽象**——routes / services / registry 强制分离，便于未来 v0.3+（多并发分布式 / 鉴权 / 第三方 SDK）扩展
- **API 版本化**——`/api/v1/` 路径前缀，未来 v2 不冲突

### 11.4 v0.2 仍不追求

1. 大规模分布式（v0.3 才考虑 Redis / 多进程 server）
2. 鉴权（v0.2 单用户本地；v0.3+ 加 token / OAuth）
3. 多用户 SaaS（v0.4+）
4. 自动建模助手（属第二阶段 LLM 辅助建模 PoC）
