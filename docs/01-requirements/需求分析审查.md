# 需求分析审查

## 一、文档用途

本文件不再重复需求正文，只保留两类内容：

1. 当前仍需重点关注的风险与问题
2. 当前仍需在系统设计阶段确认的问题

它的作用是作为**审查清单和风险清单**。

## 二、当前主要风险

### 3.1 可信度风险

最大风险不是功能做不出来，而是：

**结果是否足够可信，能不能让用户拿来辅助判断。**

### 3.2 成本风险

如果过多实体都使用 LLM，多轮仿真成本会快速上升。

### 3.3 抽象失控风险

如果系统设计阶段过度追求通用性，容易做出一个抽象很多、但无法落地的架构。

### 3.4 配置门槛风险

如果世界定义和场景文件太复杂，用户将无法有效使用引擎。

## 三、系统设计阶段待确认事项

以下问题还没有完全落定，进入系统设计时必须逐条确认：

1. **世界定义文件格式**
   - 第一版 YAML 的层级和字段如何组织

2. **场景文件格式**
   - 实体、关系、环境、事件、断点、配置如何组织

3. **动作效果表示方式**
   - 如何表达“改属性 / 改关系 / 发消息 / 改环境”

4. **消息总线设计**
   - 消息如何路由、存储、投递、过滤

5. **轨迹存储结构**
   - 每轮快照保存哪些字段
   - 即时分析如何读取轨迹摘要

6. **LLM 输出 Schema**
   - 动作选择和参数输出结构如何定义

7. **干预接口**
   - 外部如何调用暂停、分析、注入消息和修改状态

8. **分析模块结构**
   - 即时分析和最终报告是否共享同一套输入摘要逻辑

## 四、实现优先级提醒

### P0：必须先做

1. 世界定义
2. 场景实例化
3. 基础仿真循环
4. 混合决策
5. 轨迹记录
6. 暂停与即时分析

### P1：第一版应做

1. 冲突解决
2. 环境主动事件
3. 感知范围
4. 人工干预
5. 持久化与断点续跑

### P2：后续扩展

1. 实体动态增删
2. 回滚
3. 分布式扩展
4. 可视化增强

## 五、审查结论

当前文档已经具备进入系统设计的条件。

系统设计阶段应避免两种错误：

1. 抽象过度，导致迟迟无法进入原型验证
2. 抽象不足，导致第一版只能服务一个场景

正确目标应该是：

**先为首个 MVP 场景设计出最小但可复用的通用内核。**

## 六、未来演化提醒

系统设计时应显式为未来演化预留空间：

1. 第一版以 `World Definition + Scenario + Rules + Event Log + Runtime` 为核心
2. 不把语义增强层作为运行核心
3. 但字段设计和概念命名应尽量保持语义清晰，方便未来接入知识图谱和语义增强能力

这意味着第一版不是否定语义能力，而是把它放到更合适的未来位置：

**语义增强层，而不是仿真运行核心。**
